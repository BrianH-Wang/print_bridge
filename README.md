# Print Bridge (V1.0.0)

**中文** | [English](README.en.md)

一个跨平台（Windows / macOS / Linux）的**本地打印与数据中转服务**，带 PyQt6 图形界面。

它解决的问题是：浏览器 / Web 页面无法直接调用本机打印机，也无法直接接收第三方系统的回调数据。本程序作为常驻本机的"桥梁"，一端用 WebSocket 与前端页面通讯，另一端调用系统打印机并接收外部 HTTP 回调。

## 主要功能

程序由两个可独立开关的模块组成，在界面上勾选启用。

> **前端只需连一条 WebSocket**（默认 `ws://localhost:8765`，端口在「前端连接」卡片配置，可选 1024–65535）。
> 打印和数据推送**共用这一条连接**，因此只要勾选了任意一项功能，WebSocket 服务就会启动 ——
> 即使不用打印机、只用「获取数据」，前端一样连得上、收得到数据。

### 1. 自动打印 🖨

- 前端用一条 `print` 消息把打印任务发过来（见下面「多台打印机」）；也兼容老的**二进制帧**用法（打到默认打印机）。
  服务端把 PDF 保存到系统临时目录（文件名带时间戳，不会互相覆盖），再调用系统打印机打印：
  - Windows：`win32api.ShellExecute(..., "print", ...)`
  - macOS / Linux：`lp -d <打印机名>`
- 打印结果通过 `{"type": "print_status", "data": "✅ 成功" / "❌ 失败"}` 回传给前端。
  未勾选「自动打印」时若收到 PDF，会回 `"❌ 未启用自动打印"` 并忽略，不会尝试打印。
- 前端可先发一条 `{"type": "printWithTime", "timeInfo": {...}}` 文本消息带上耗时信息（`apiTime`、`prepareTime`、`startTime`），服务端据此在日志中统计接口耗时、准备耗时和端到端总耗时。
- 打印机列表自动枚举（Windows 走 `win32print`，macOS/Linux 走 CUPS），并预选系统默认打印机。

#### 多台打印机：一单三张（每个方案单独配）

一个门店同时接小票机、后厨机、杯贴机是常见需求。配置里每台打印机有一个**英文 key**（前端用）
和一个**中文备注**（给人看）：

| Key | 备注 | 方式 | 目标 | 默认 |
| --- | --- | --- | --- | --- |
| `receipt` | 小票 | 系统队列 | HPRT_SL42 | ★ |
| `kitchen` | 后厨 | 网络直连 | 192.168.1.51:9100 | |
| `cup` | 杯贴 | 网络直连 | 192.168.1.52:9100 | |

前端发打印任务时点名打给谁：

```jsonc
// 前端 → Print Bridge，三张各发一条，不用等上一条回来
{"type": "print", "printer": "kitchen", "jobId": "a1",
 "format": "base64", "data": "<base64 的 PDF>"}      // format 也可以是 "text"，直接发 ZPL/TSPL
// Print Bridge → 前端，每条任务各回一条
{"type": "print_status", "printer": "kitchen", "jobId": "a1", "data": "✅ 成功"}
```

- `printer` 不填就打到 **★ 默认那台**（表格第一行，「设为默认」= 挪到第一行）。
- 名字不存在时明确回 `❌ 没有名为 xxx 的打印机（可用：receipt、kitchen、cup）`，不会静默打到别处。
- `format`：`base64`（PDF 等二进制）或 `text`（ZPL / TSPL / ESC-POS 指令流）；解码失败会回明确错误。
- **为什么用一条自包含的 JSON 而不是「先发文本再发二进制」**：后者靠到达顺序配对，
  同一条连接上并发三个任务时会配错（现有 `printWithTime` 就有这个隐患）。一条消息带齐信息就没有配对问题。

**并发模型**：

- **不同打印机并行**：三张同时开打，总耗时 ≈ 最慢那台，不是三台之和。
  实测小票 0.1s / 后厨 1.2s / 杯贴 0.1s 同时发出，回执到齐 1.21s（串行会是 1.4s）。
- **同一台打印机串行**：同一台上的任务排队执行，不会两份数据在一个 socket 上交叉。
  实测同一台连发两条 0.5s 的任务，区间是 0→0.5、0.5→1.0，而另一台的任务在这期间并行跑完。
- 一台卡住不影响另外两台——每台一把锁，不是一把全局锁。
- 打印任务在后台跑，不阻塞这条 WebSocket 上的其它消息（数据推送、ack 照常）。

**谁决定打几张**：前端。服务端只负责「按 key 送达 + 回执」，不碰排版和内容。
双向模式下，前端可以等三条 `print_status` 都回来后再回 `external_reply`，
设备拿到的就是「小票成功、杯贴缺纸」这种真实结果。

#### 打印方式：系统打印机 / 网络直连（每台单独选）

每台打印机各自选，同一套配置里可以混用：

| 方式 | 走什么 | 适用 |
| --- | --- | --- |
| **系统打印机** | PDF 落临时目录 → `lp -d <队列名>` / `ShellExecute("print")` | USB、蓝牙、WiFi、网口——**只要在系统里装成打印队列**都走这条 |
| **网络直连** | 直接连打印机的 RAW 端口（默认 9100），把前端发来的字节**原样写进 socket** | 没装系统队列的网络标签机，前端直接发 ZPL / TSPL / ESC-POS 指令 |

- 非直连打印机（蓝牙 / WiFi / 网口）**不用在本程序里配**，在系统里加好队列即可：
  - macOS：系统设置 → 打印机与扫描仪 → 添加 → IP 标签页 → 协议选 `HP Jetdirect - Socket`（9100）或 `LPD` / `IPP`；
    命令行等价 `lpadmin -p 队列名 -E -v socket://192.168.1.50:9100 -m everywhere`（型号用 `lpinfo -m` 查）。
  - Windows：添加打印机 → 我需要的打印机不在列表中 → 使用 TCP/IP 地址添加 → 标准 TCP/IP 端口 9100。
  - 蓝牙：先在系统蓝牙里配对，配对后一般会自动出现打印队列。
  - 加完 `lpstat -v` 能看到设备 URI，回到界面点「刷新」就能在下拉里选到。
- **网络直连是透传，不做任何转码**：前端发 ZPL 就发 ZPL，发 PDF 就发 PDF ——
  打印机认不认得这份数据由前端保证（多数标签机不认 PDF，要发指令流）。
- 填好 IP / 端口后可以点「测试连接」，只做一次 TCP 连接探测，确认网络通不通，不会真打一张。

### 2. 获取数据 🌐（HTTP 回调接收）

- 在 `localhost:13213` 启动一个 HTTP 服务，接收外部系统 `POST` 过来的 JSON 数据。
- **监听地址可自定义**：直接改成 `192.168.1.50:18000` 这类地址即可。写法很宽松：`http://` 前缀可省、
  端口可省（默认 13213）、结尾多余的 `/` 会自动去掉；格式不对时下方提示立刻变成 ⚠️，点启动也会被拦下来。
  - 主机名照填即可：填 `0.0.0.0` 就是监听所有网卡，让局域网内的其他机器也能推过来。
  - 地址里的**路径部分只是给人看的示例**，真正决定收不收、怎么收的是下面的「接收通道」。
- 收到后（可选地转译字段，见下）立即广播给**所有**已连接的前端：
  `{"type": "external_data", "id": "…", "channel": "<通道 key>", "data": {…}}`
- 对调用方返回统一 JSON 响应（形状可按通道自定义，见下文）。
- 另提供 `GET` 健康检查，返回当前在线的 WebSocket 客户端数和已配置的通道列表。

#### 接收通道：一条链接一套规矩（每个方案单独配）

一台设备常常有**多个接口**——比如分拣机的「数值推送」和「图片上传」是两条链接，
一条要等前端算出分拣格口才能回，另一条收下就该立刻放行。一份全局设置盖不住这种组合，
所以每条链接是一条独立的**通道**：

| 列 | 说明 |
| --- | --- |
| Key | 英文标识。转发给前端的报文里带 `channel` 字段，前端据此区分数据来源 |
| 备注 | 中文，只给人看 |
| 路径 | 设备 `POST` 的路径，如 `/callback`。填 `*` 表示**兜底**：没被别的通道认领的路径都归它 |
| 方向 | 单向 / 双向，见下 |
| 超时 | 双向下设备最多等多久 |
| 配对 | 在配对合流里的角色，见下 |
| 应答外壳 | 默认 / 自定义，见「HTTP 响应配置」 |

- 路径**不区分大小写**，结尾的 `/` 和 `?参数` 会自动忽略：设备填 `/Callback`、这里填 `/callback` 是同一条。
- **单发排队按通道各排各的**——图片通道慢的时候不会把数值通道一起堵死。
- 没有兜底通道时，未匹配的路径回 `404`；提示行会明确警告这一点。
- 从旧版本升级上来的方案会自动迁移成**一条兜底通道**，行为和以前完全一样，不用重配。

#### 字段映射：设备的字段名 → 前端要的字段名（每条通道单独配）

中间件的活儿：设备接口写死了叫 `code`，前端接口写死了叫 `expressNo`，两边都改不动，
就由这里翻译。通道对话框的「字段映射」页：

| 模式 | 效果 |
| --- | --- |
| 原样透传（默认） | 不改动，等于不配置 |
| 只保留映射的字段 | 只留下表里列出的，改名 + 转换，其余丢弃 |
| 透传 + 追加映射的 | 原字段全留，再追加映射出来的；改了名的会把原名去掉 |

字段表每行：**来源字段 → 目标字段 + 转换 + 必填 + 默认值**。

- 来源支持嵌套路径：`order.id`、`items[0].sku`。
- 转换算子：去空格 / 大小写 / 转数字 / 转文本 / base64 解码 / 秒或毫秒时间戳转日期时间。
  手改 json 还能用带参数的 `prefix` `suffix` `replace` `lookup`（查表替换，如承运商代码转中文名）。
- 必填字段缺失时可选：**回错误给设备** / 跳过该字段 / 用默认值。回错误时数据不会转发给前端。
- **「按样例填充」**：把设备实际发来的一条 JSON 粘进样例框，一键把所有字段列成映射行，
  只要改右边的目标名——不用自己琢磨路径怎么写。
- 下方**实时预览**：左边样例、右边算出的结果，改一个算子立刻看到效果。

> 不提供代码框（Python / JS 脚本块）。方案是会被导出、复制到别的门店、发在群里的，
> 里面存一段可执行代码等于谁拿到配置谁就能在这台连着打印机的电脑上执行任意代码。
> 覆盖不了的需求就加算子，不加 `eval`。

#### 发给前端的报文形状（每条通道单独配）

前端已经有自己的接口、连外层都对不上时，在「发给前端 ⚙」页改：

- **消息 type**：默认 `external_data`，可改成 `parcel_scanned` 之类。
- **固定附加字段**：每条报文都带上，如 `{"source": "仓库A"}`。
- **整条报文自己写**：勾上后用模板决定整条报文，标准的 `type/id/channel/data` 外层全部不要了。

  ```jsonc
  { "cmd": "parcelImage", "seq": "{{__id}}",
    "expressNo": "{{expressNo}}", "img": "{{imageBase64}}" }
  ```

  模板里可以用**映射后的字段名**，加上 `{{__id}}` `{{__channel}}` `{{__label}}` `{{__path}}` `{{__data}}`。
  和应答外壳一样，整串就是一个占位符时按原类型替换。
- **`{{__id}}` 必须出现**，否则前端的回复和 ack 都对不上号——保存时强校验。

> ⚠️ **入向还没做**：自定义模板改的是「我们发给前端」的形状。前端**回**给我们的
> 仍然必须是 `{"type":"external_reply","id":…}` 和 `{"type":"ack","id":…}`。
> 前端那侧也完全改不动时，需要「入向识别规则」，见 [docs/高级配置.md](docs/高级配置.md) 的 X8，还没实现。

「重发」历史记录时走的是同一条组装链路——历史里存的是设备发来的原始数据，
重发时按**当前**通道配置重新转译一遍，不会出现重发的形状和当初推的不一样。

#### 配对合流：两条链接合成一条（每条通道单独配）

一台设备常常把一件事拆成两个接口发：分拣机的**图片**走 `/upload`、**数值**走 `/callback`，
靠同一个条码算一件。前端要的是「一条带图的记录」，不是两条对不上的消息。

```
设备A ──POST /upload ──▶ ┐  code=A123（收下就回，不推前端）
                         ├─▶ 按 code 配对 ─▶ 合成一条 ─▶ 前端
设备B ──POST /callback ─▶ ┘  code=A123（等图齐了再发）
```

在通道的「配对」页设角色：

| 角色 | 行为 |
| --- | --- |
| 不参与配对（默认） | 照常各发各的 |
| **主报文** | 先等同组的附加数据齐，再把合并后的结果发给前端 |
| **附加数据** | 收下存进暂存区、立刻回 200，**不推给前端**，等主报文来取 |

- **两边不对称**：附加通道天生是单向的（收下就回），所以「先到的那条怎么应答」
  根本不是问题——界面上它的「数据流」会被锁成单向。
- **配对字段取的是「字段映射」转译之后的名字**。两条通道源字段名不一样时
  （一边 `code`、一边 `orderNo`），各自先在映射里改成一致即可。
- **谁先到都行**：图片先到就存着等；数值先到就挂起等图，图一到立刻继续。
- **等图和等前端回复共用同一份超时预算**，设备最多等它配的那个秒数，
  不会变成「等图 5s + 等回复 10s」。
- 等不到时可选**照发**（缺的字段就没有，默认）或**回错误给设备**（504 配对超时）。
- 并入规则：默认把附加数据里**除配对键外的字段全并进主报文**；
  也可以指定只并某一个字段，并给它改个名。
- 暂存区有**过期时间**（默认 60s）和**条数上限**（默认 200）：
  只发图不发数值时，那些图不会一直挂着把内存吃光。
- 启动前会检查配对组的搭配：只有主报文没附加、只有附加没主报文、
  一组里多条主报文、两边配对字段不一致，都会拦下来并说清怎么改。

> ⚠️ 设备如果是**同一个连接顺序发**——先发数值、阻塞等响应、拿到响应才发图片——
> 那图片永远发不出去，配对必然超时。这种设备只能让它**先发图片**，
> 或者把两条请求放在各自独立的连接上。`tools/mock_device.py --parallel` 就是模拟后者。

#### 数据流：单向 / 双向（每条通道单独配）

```
单向  设备 ──POST──▶ Print Bridge ──WS──▶ 前端
                        └──── 立即 200 ────▶ 设备        （不等前端）

双向  设备 ──POST──▶ Print Bridge ──WS──▶ 前端
                                   ◀─ external_reply ─┘
           ◀── 200 + 前端的回复 ────┘                    （超时则 504）
```

- **单向**：转发完立刻回 `{"success": true, "code": 200, "forwarded": n}`，就是原来的行为。
- **双向**：推给前端的消息多带一个 `"expectReply": true`，然后**阻塞等前端回一条**：

  ```jsonc
  // 服务端 → 前端
  {"type": "external_data", "id": "788164362335fcf5", "channel": "sorter_data",
   "expectReply": true, "data": {...}}
  // 前端 → 服务端（id 原样带回，data 是要回给设备的内容）
  {"type": "external_reply", "id": "788164362335fcf5", "data": {"ok": true, ...}}
  ```

  拿到回复后答复设备 `{"success": true, "code": 200, "message": "前端已处理并回复", "data": <前端的回复>}`。
  多个前端都连着时以**最先回来的那条**为准，后到的丢弃并记一条日志。
  双向模式下这条回复同时当作 ack，前端不必再单发 `{"type":"ack"}`。
- **超时**（`超时(秒)`，0.1–600，默认 10）：等不到回复就回 `504`
  `{"success": false, "code": 504, "error": "等待前端回复超时（10s）"}`。迟到的回复会被忽略。
  双向模式下如果一个前端都没连，直接回 `503`，不做无谓的等待。

#### 并发 / 单发（每条通道单独配）

- **并发**（默认）：多条请求各走各的，第 2 条不必等第 1 条回来。
  实测三条 delay 1.5s / 0.3s / 0.3s 同时打进来，总墙钟 1.5s。
- **单发**：排队串行，一条处理完（拿到回复或超时）才轮到下一条。
  用的是**叫号**而不是普通锁——普通锁不保证先到先得，三条排队时完成顺序可能变成 2、3、1，
  设备侧看到的次序就乱了。实测三条 0.6s 的请求依次完成，间隔 0.6s，顺序 1→2→3。
- 单发模式下**排队和等回复共用同一份超时预算**，设备最多等你配的那个秒数，
  不会因为前面排了两条就被晾成 3 倍时长；排队没轮到就回 `503`。
  某条超时放弃后队列会自动跳过它，不会把后面的人卡死。

#### HTTP 响应配置（全局，「HTTP 响应」按钮）

回给设备的**状态码和说明都可以改**，按「场景」而不是按状态码维护——同一个 503 既可能是没人接、
也可能是排队没轮到，分开才说得清是哪一种问题：

| 场景 | 默认码 | 默认说明 | 什么时候返回 |
| --- | --- | --- | --- |
| 接收成功（单向） | 200 | 数据已接收并处理 | 单向模式转发完立即返回 |
| 接收成功（双向） | 200 | 前端已处理并回复 | 双向模式拿到回复，body 的 `data` 是回复内容 |
| 请求体不是合法 JSON | 400 | JSON 解析失败：`{error}` | body 解析失败 |
| 请求体过大 | 413 | 请求体过大，上限 `{limit}` 字节 | 超过 16MB |
| 没有前端连接 | 503 | 无 WebSocket 客户端连接，无法取得回复 | 双向模式下一个客户端都没连着 |
| 排队超时 | 503 | 单发模式排队等待超过 `{timeout}s` | 单发模式排到超时都没轮到 |
| 等待回复超时 | 504 | 等待前端回复超时（`{timeout}s`） | 双向模式前端没在超时内回 `external_reply` |
| 路径没有对应通道 | 404 | 没有匹配该路径的通道：`{path}` | POST 的路径没匹配上，也没有兜底通道 |
| 字段转译失败 | 400 | 字段转译失败：`{error}` | 必填字段缺失或转换算子出错，数据没转发给前端 |
| 配对超时 | 504 | 等不到配对数据（`{missing}`），超时 `{timeout}s` | 主报文没等到附加数据，且设了「回错误」 |

- 说明里的 `{error}` / `{timeout}` / `{limit}` / `{path}` / `{missing}` 会在返回时替换成实际值，删掉也不影响（不会因为文案报错）。
- 「全部恢复默认」一键把 10 个场景全改回上表的出厂值。
- 改完**立即生效**，服务运行中也不用重启；配置存在 `QSettings` 的 `http_responses` 键里，全局共享（错误语义跟仓库无关，不进方案）。
- 非法值（码不在 100–599、认不出的场景）会被忽略并落回默认，手改坏了 json 也只是回到默认值。
- 通道可以**按场景覆盖**其中几条，叠加顺序是 **通道覆盖 > 上面这张全局表 > 出厂默认**。

#### 应答外壳（通道的「高级」页）

上表管的是**状态码和文案**，body 长什么样是另一件事。默认形状是
`{"success": …, "code": …, "message"/"error": …}`，但对接方的接口文档往往写死了别的形状——
比如要求字段叫 `msg` 而不是 `message`，或者不许出现多余字段。这时在通道的「高级」页
勾上「自定义应答外壳」，写一个模板：

```jsonc
{ "success": "{{__success}}", "code": "{{__code}}",
  "msg": "{{__message}}", "data": "{{__data}}" }
```

- 可用变量：`{{__success}}` `{{__code}}` `{{__message}}` `{{__data}}` `{{__forwarded}}` `{{__scene}}` `{{__channel}}`。
- **整串就是一个占位符时按原类型替换**：`"code": "{{__code}}"` 出的是数字 `200`，不是字符串 `"200"`——
  按文档做严格类型校验的设备才认。夹在文字里（`"第 {{__code}} 号"`）则按字符串拼接。
- 下拉里有几个**常用形状**可以一键套用，不用对着空白模板从头写。
- 对话框下方**实时预览**渲染结果；模板不是合法 JSON、用了不存在的变量、或漏了 `{{__code}}`／`{{__message}}`，
  当场标红并且存不进去。
- 「HTTP 状态码」还可以选**固定 200**——有些设备把非 200 一律当网络故障、压根不看 body。
- 不勾这个开关时用内置形状，**和不配置时完全一样**。

更完整的分层设计（含还没做的字段转译、配对合流）见 [docs/高级配置.md](docs/高级配置.md)。

### 3. 配置方案 📁（一个仓库一套配置）

- 顶部「配置方案」卡片把整套配置打包命名保存：**WebSocket 端口、打印机列表（可多台，每台各自选系统队列或 IP:9100）、
  监听地址、两个功能开关、接收通道列表（每条各自的路径 / 单双向 / 超时 / 并发 / 应答外壳）**。
  例如「仓库A」= 端口 8777 + 打印机 HTSS + 监听 `localhost:1111` + 一条 `/join` 双向 8s 单发通道，
  「仓库B」= 端口 9111 + 打印机 BBB + 监听 `localhost:3333` + 一条 `/callback` 单向并发通道。
- **快速切换**：下拉选中哪套，界面上这一整套配置就换成哪套，不用一个个改。

#### 导出 / 导入 / 模板

通道那套东西（路径、字段转译、配对、报文形状）配一次要花点工夫，但**只需要配一次**：

| 按钮 | 干什么 |
| --- | --- |
| **导出** | 把当前方案存成一个 json，发给别的门店或留底。服务运行中也能点（纯读） |
| **导入** | 从 json 装回一套方案。方案重名时会问「覆盖 / 另存为新的 / 取消」，**绝不静默覆盖** |
| **模板** | 从配好的模板开始，可以「保存为文件」慢慢改，也可以「直接套用」建一套新方案 |

- 导出的是**界面上此刻的样子**，不是上次保存的样子——有未保存改动时导出个旧版本最坑人。
- 导出内容：WebSocket 端口、监听地址、两个功能开关、打印机列表、通道列表
  （含字段映射、配对、报文模板、样例），以及全局的 HTTP 应答表——
  只发通道不发应答等于只装了一半。
- 内置两套模板：**空白起步**（一条兜底通道，照着填）和
  **几何智造分拣设备**（`/callback` + `/upload` 两条链接，配对与应答外壳都已配好，
  导入后直接就能对接）。
- 导入的文件必须带 `print-bridge-config` 标记；不是本程序导出的、或版本比程序新，
  都会明确告诉你原因，不会装进去一半。

> 这就是「高级配置只需要被配一次」的落点：懂技术的人配好导出，
> 其他门店导入即可，不用打开那两页 ⚙。
- 五个按钮：
  - 「保存」把界面上当前的配置写回选中的方案；下方提示会实时显示「有未保存的修改 / 已保存」。
  - 「新建」用当前配置另存为一套新方案（弹窗输入名称，例如 `仓库A`），最多 20 套。
  - 「重命名」「删除」维护方案列表（至少保留一套；删掉默认方案时默认位自动落到第一套）。
  - 「设为默认」给方案打上 ★，**程序启动时自动载入这一套**。
- 有未保存的修改时切换方案会先弹窗确认，避免改了一半的配置被静默丢弃。
- 方案列表以 JSON 存在 `QSettings` 里（键 `profiles` / `default_profile`），换机器时可直接拷这一项。
- 方案里记的系统队列在本机不存在时（换了台机器 / 打印机没开），不会静默改选别的打印机：切换方案时日志提示，点启动时明确拦下来。
- 服务运行中整张卡片和其余配置项一起禁用，停止后才能改。
- 方案在 `QSettings` 里的字段：`ws_port`、`printers`（数组，每项 `key`/`label`/`kind`/`queue`/`host`/`port`）、
  `data_addr`、`enable_print`、`enable_data`、`flow_mode`、`reply_timeout`、`dispatch_mode`。
  旧版本的单打印机字段（`printer`/`print_target`/`printer_host`/`printer_port`）会自动迁移成列表里的一台，老方案不用重配。

### 界面

- 顶部常驻「启动/停止」按钮与状态条，在任何页签下都能启停、都看得到服务状态。
- 三个页签：「配置 ⚙」（配置方案、功能开关、端口、打印机、数据获取，整体可滚动）、
  「日志输出 📋」、「接收历史 📜」。配置一次设好就不动，日常盯的日志和历史各占满整个窗口。
- 日志：各服务线程通过 `queue.Queue` 把日志推给 GUI，界面每 300ms 批量刷新一次，最多保留 2000 行；可切换自动滚动、一键清空。
- **接收历史与重发**：每条从 `/callback` 收到的数据都会记进表格，最新的在最上面，最多保留 200 条，页签标题实时显示条数。
  - 列是**按收到的字段动态生成的**：「时间」在最左，「图片」「推送」在最右，中间每个 JSON 字段各占一列（`expressNo`、`weight`……）。出现新字段会自动插入新列，旧行该列留空。
  - **图片列直接显示缩略图 + 类型和大小**（如 `PNG · 1.0 MB`），**双击可放大查看**。类型按文件头识别，支持 PNG / JPEG / GIF / BMP / WEBP / PDF，也认 `data:image/png;base64,` 前缀。单张超过 5MB 不落盘，但仍记录类型和大小。
  - 其余超长字段在单元格里折叠成「头部....尾部[N字符]」，悬停可看完整摘要。
  - 选中任意一条点「重发选中」，即可把这条数据**原样**重新推送给所有已连接的前端（双击留给图片放大，避免误触重发） —— 表格里显示的是折叠摘要，重发时用的是完整原始数据（含完整 base64）。
  - 前端调试时不用再让外部系统重新推一次。无客户端连接时重发会提示未送达。
  - **图片存磁盘、不占内存**：收到数据时图片单独写成文件，内存里只留一张小缩略图，其余字段照常保留。
    实测收 200 单、每张图约 1MB：磁盘 207MB，**内存零增长**（RSS 反而略降）；`history.jsonl` 仅 43KB，因为里面不含 base64。
    表格上方实时显示「共 N 条 · 图片 X MB 存在磁盘（不占内存）」。

- **历史持久化**：每收到一条就立刻追加写盘，程序关闭/崩溃都不丢；下次启动自动载入最近 200 条（含缩略图）。

  ```
  logs/                      ← 默认在程序所在目录，不存在会自动创建
    history.jsonl            ← 每行一条元数据（不含图片 base64）
    images/
      20260818_115425_071713.png        ← 原图，重发时从这里读回
      20260818_115425_071713_thumb.png  ← 缩略图，启动时只读它，不必解码原图
  ```

  - 目录可在「接收历史」页签里点「更改目录」切换（记在 `QSettings`，下次启动沿用），「打开目录」直接在访达/资源管理器里打开。
  - 「清空历史」会删除记录和图片文件，因此会先弹窗确认。
  - 超过 200 条时，最旧的记录连同它的图片文件一起删除，磁盘不会无限增长。
- **主题：白天 / 黑夜 / 跟随系统**，右上角分段控件一键切换，选择会记住（`QSettings`），下次启动自动恢复。
  - 选「跟随系统」时，系统在浅色/深色之间切换会实时跟着变，无需重启。
  - 通过 Qt 的 `setColorScheme` 同时切换原生控件（复选框、下拉箭头、滚动条）的配色，不会出现深色背景配浅色控件的割裂感。
  - 配色集中在 `theme.py` 的 `PALETTES` 里，改颜色不用动样式表结构。

## 数据流

```
前端页面 ──WS print(printer=receipt)──▶ websocket_handler ──▶ 小票机(系统队列)
         ──WS print(printer=kitchen)──▶                  ──▶ 后厨机(:9100)
         ──WS print(printer=cup)────▶                    ──▶ 杯贴机(:9100)
         ◀──WS print_status(printer, jobId)──────────────────┘   （三台并行）

单向  外部系统 ──POST JSON──▶ HTTP :13213/callback ──转发──▶ 前端页面(WS external_data)
双向  外部系统 ◀── 200+回复 ── HTTP :13213/callback ◀─回复── 前端页面(WS external_reply)
```

## 首次启动被防火墙 / Gatekeeper 拦截

**macOS**:`Print Bridge.app` 没有 Apple Developer 签名时,首次双击会被 Gatekeeper 拦下,显示"无法打开,因为无法验证开发者"。处理方式,任选其一:

```bash
# 1) 自己/团队内部用:删掉隔离属性,以后不再被拦
xattr -dr com.apple.quarantine "/Applications/Print Bridge.app"

# 2) 或者在 Finder 里:右键(按住 Ctrl 点)Print Bridge.app → "打开" → 在弹窗再点"打开"
#    之后系统记住它,双击就可以直接进。

# 3) 正式分发:申请 Apple Developer ID(年费),做 codesign + notarytool 公证,
#    这样任何 mac 都能直接装,不弹警告。
```

`Print Bridge.app` 启动后系统防火墙会在「隐私与安全 → 防火墙」里提示是否允许接受网络连接(因为内置 HTTP :13213 与 WebSocket 服务都需要监听端口),**点"允许"**;启动过一次之后再启不会重复询问。

**Windows**:SmartScreen 弹出"Windows 已保护你的电脑" → 点"更多信息" → "仍要运行",只在首次出现。系统的 Defender 防火墙同理,首次会弹"是否允许此应用通过防火墙",勾上"专用网络"和"公用网络"都行,因为它只监听本地回环。

**Linux**:不需要特别处理,AppArmor / iptables 之类通常不拦截用户进程直接跑的 GUI 程序,直接 `./print_bridge/print_bridge` 即可;若服务端口被 SELinux 拦截会报 `permission denied`,改用临时 `setenforce 0` 排除。

## 说明与限制

- 启动后会回查端口是否真的绑定成功;被占用时状态栏变红提示并自动回滚到「已停止」,不会显示成运行中。
- WebSocket 监听地址：Windows 上绑定 `localhost`，macOS / Linux 上绑定 `0.0.0.0`。
- 数据获取地址可在界面上自由填写，并随「配置方案」整套切换；默认仍是 `localhost:13213/callback`。
- 待打印的 PDF 写在系统临时目录的 `print_application_server/` 下，超过 24 小时的旧文件会在下次打印时自动清理。
- 日志中超过 60 字符的字段会折叠成「头部....尾部[N字符]」，避免 base64 图片刷屏；**转发给前端的仍是完整数据**。
- 打印本身是阻塞操作，已放到独立线程执行，不会卡住 WebSocket 消息收发。
