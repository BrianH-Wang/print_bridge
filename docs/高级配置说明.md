# Print Bridge 高级配置说明

给**负责对接的人**看的：设备的接口文档和前端页面的接口都已经写死、两边都改不动时，
怎么在 Print Bridge 里把它们接上。需要看得懂 HTTP 请求和 JSON。

日常操作（启动、导入配置、看日志）见 [使用说明](使用说明.md)。English version: [Advanced Guide](Advanced%20Guide.md).

---

## 一、先搞清楚三件事

### 1. 高级配置只需要配一次

```
模板 / 导入          绝大多数人停在这一层：套一个现成配置，什么都不填
    ↓
基础 / 字段映射 / 配对   会看 JSON 就够：改路径、改字段名、勾配对
    ↓
两页 ⚙              要懂 HTTP + JSON：改报文形状、改应答外壳、写模板
```

对接的人在一台机器上配好 → 「配置方案」卡片点「**导出**」存成 `.json` →
其他机器全部「**导入**」。不会开发的人永远不用打开 ⚙ 页。

### 2. 铁律：全部默认 = 和不配置一模一样

⚙ 页里每一项的默认值就是程序原本的行为。不勾、留空、保持默认，行为不变。
所以只改你确认要改的那一项，其余别动。

### 3. 动手前准备好这两样

| 准备什么 | 用来干什么 |
| --- | --- |
| **设备实际发来的一条数据**（让设备方发一条真的，或从日志 / 接收历史里复制） | 粘进「样例」框，所有预览和自测都靠它 |
| **设备接口文档里「返回值」那一节** | 决定「回给设备 ⚙」页要不要改、改成什么形状 |

前端页面那侧还要知道它**收**什么形状、**回**什么形状，见第四节。

## 二、通道的基础规则

一条通道 = 设备的一个接口。「获取数据配置」→「添加」，「基础」页：

| 项 | 规则 |
| --- | --- |
| **Key** | 小写字母开头的英文标识，最长 20 个字符。前端收到的报文里 `channel` 字段就是它 |
| **路径** | 设备 POST 地址里 `/` 后面那段。**不区分大小写**，结尾的 `/` 和 `?参数` 自动忽略：设备发 `/Callback/`、这里填 `/callback` 是同一条 |
| **路径填 `*`** | 兜底通道：没被别的通道认领的路径都归它。没有兜底通道时，未匹配的路径回 404 |
| **数据流** | 单向：转给前端后立刻回设备。双向：等前端回一条，用它答复设备 |
| **超时** | 只对双向有效，0.1–600 秒。等不到回 504 |
| **分发** | 并发：多条请求同时处理。单发：本通道排队，一条处理完才轮到下一条，别的通道不受影响 |

**超时预算只有一份。** 双向通道里，排队等待、等配对数据、等前端回复三段时间加起来不超过你填的超时秒数，
设备最多等这么久，不会变成三段相加。排队没轮到回 503，配对等不到按配对设置处理，前端没回回 504。

「基础」页下半部分「**这条通道怎么用**」会随你的设置实时生成一条 `curl` 命令和一段行为说明，可以直接发给设备方。

## 三、字段映射：设备的字段名 → 前端要的字段名

通道对话框的「字段映射」页。设备发 `code`，前端要 `expressNo`，在这里翻译。

### 3.1 三种模式

| 模式 | 前端拿到什么 |
| --- | --- |
| **原样透传（不改动）** | 设备发什么给什么。默认，等于没配 |
| **只保留下面映射的字段** | 只有表里列出的字段，改名、转换之后的样子；其余全丢 |
| **原样透传 + 追加映射的字段** | 原字段全留，再追加映射出来的。改了名的字段会把原名去掉，前端不会同时看到 `code` 和 `expressNo` |

### 3.2 字段表的每一行

| 列 | 填什么 |
| --- | --- |
| **来源字段** | 设备发来的字段。支持嵌套路径：`order.id`、`items[0].sku`、`a.b[2].c` |
| **目标字段** | 前端要的名字。留空等于和来源同名 |
| **转换** | 见下表，可不选 |
| **必填** | 勾上后，设备没发这个字段时按「必填字段缺失时」的策略处理 |
| **默认值** | 字段缺失且策略是「用默认值」时填进去的值 |

「**按样例填充**」：把样例里的字段一次全列进表，你只改目标字段那列。样例里嵌套的对象会往下摊三层。

### 3.3 转换算子

下拉里能选的：

| 算子 | 效果 | 例子 |
| --- | --- | --- |
| 去掉首尾空格 | `" A01 "` → `"A01"` | |
| 转大写 / 转小写 | `"sf123"` → `"SF123"` | |
| 转数字 | `"12.50"` → `12.5`，`"12.0"` → `12` | 设备把数字发成文本时 |
| 转文本 | `12` → `"12"` | |
| base64 解码成文本 | 解出 UTF-8 文本 | 设备把 JSON 再 base64 一层时 |
| 毫秒 / 秒时间戳 → 日期时间 | `1767225600000` → `"2026-01-01 12:00:00"` | |

只能手改配置文件才用得上的（带参数）：

| 算子 | 写法 | 效果 |
| --- | --- | --- |
| 加前缀 | `{"op": "prefix", "value": "SF"}` | `"123"` → `"SF123"` |
| 加后缀 | `{"op": "suffix", "value": "-A"}` | `"123"` → `"123-A"` |
| 替换文本 | `{"op": "replace", "from": "-", "to": ""}` | `"12-34"` → `"1234"` |
| 查表替换 | `{"op": "lookup", "table": {"1": "华东", "2": "华南"}, "default": "其他"}` | `"1"` → `"华东"`，查不到用 `default`，没给 `default` 就保持原值 |
| 转布尔 | `"bool"` | `"0"` / `"false"` / `""` → `false`，其余 → `true` |

手改的位置见第七节。带参数的算子在界面上会显示成「（自定义）…」，再打开保存也不会丢；
但**界面每行只显示、只保存第一个算子**，要串多个算子（先去空格再转数字）只能手改，且之后别在界面上保存那条通道的字段映射。

### 3.4 必填字段缺失时

| 策略 | 行为 |
| --- | --- |
| **回错误给设备**（默认） | 回 400「字段转译失败：缺少必填字段 xxx」，**数据不转发给前端** |
| **跳过该字段** | 前端收到的数据里没有这个字段 |
| **用默认值** | 填进「默认值」那列的值 |

**没勾必填的字段**缺失时不受这个策略影响：填了默认值就用默认值，没填就直接跳过，不会因为设备少发一个可选字段就把整条数据拒掉。

转换算子出错（比如「转数字」遇到 `"abc"`）一律按回错误处理，日志里会写是哪个字段。

### 3.5 文件校验：图片过大回 413、解不开回 415

设备文档常常规定「图片 base64 解码后不超过 2M，只收 jpg / png / pdf」，并给这两种情况各定了一个错误码。
给字段加一条 `check`（目前只能手改配置文件，位置见第七节）：

```json
{ "source": "file", "target": "imageBase64", "required": true,
  "check": { "type": "file", "max_bytes": 2097152, "formats": ["jpg", "png", "pdf"] } }
```

| 项 | 说明 |
| --- | --- |
| `max_bytes` | base64 **解码后**的字节数上限，0 或不填 = 不限 |
| `formats` | 允许的格式，按文件头识别，不看设备说它是什么。认得 `jpg` `png` `gif` `bmp` `webp` `pdf`；不填 = 不限 |

校验在字段转译**之前**跑，不过的请求不转发、不进配对暂存区，直接回设备：

| 情况 | 场景 | 默认码 |
| --- | --- | --- |
| 解码后超过 `max_bytes` | 文件过大 `file_too_large` | 413 |
| 字段缺失或为空、不是合法 base64、格式不在 `formats` 里 | 文件解析失败 `file_invalid` | 415 |

码和文案在「HTTP 响应」表或通道的 `responses` 里改（6.5）。`data:image/png;base64,` 这种前缀会自动去掉。
配了校验的字段在界面上鼠标悬停来源字段能看到校验条件，改名保存不会丢。样例过不了校验时预览会标红，自测的静态体检也会拦。

### 3.6 预览怎么看

页面下方左边是样例、右边是前端将收到的 `data`。改任何一格立刻重算，出错的行会用红字写在下面。
预览里看到的就是运行时的结果，没有第二套逻辑。

## 四、发给前端 ⚙：前端页面收到的整条报文

### 4.1 默认形状

不动这一页时，前端收到的是：

```json
{
  "type": "external_data",
  "id": "788164362335fcf5",
  "channel": "sorter_data",
  "channelLabel": "分拣数值",
  "expectReply": true,
  "data": { "expressNo": "CCSL2026083100123", "weight": 12.5 }
}
```

| 字段 | 说明 |
| --- | --- |
| `type` | 消息类型，默认 `external_data` |
| `id` | 本条消息的编号。**双向模式下前端回复时必须原样带回** |
| `channel` / `channelLabel` | 通道 Key 和备注，前端据此区分数据来自哪条链接。没填备注就没有 `channelLabel` |
| `expectReply` | 只有双向通道才有，值为 `true`，提示前端必须回一条 |
| `data` | 字段映射之后的数据；配对合流并进来的字段也在这里 |

### 4.2 前端必须回什么

**这一部分不可配置。** 不管发给前端的报文改成什么形状，前端回给 Print Bridge 的仍然固定是：

```json
{ "type": "external_reply", "id": "788164362335fcf5", "data": { "route": "A02" } }
```

`id` 原样带回，`data` 是要回给设备的内容。单向通道前端可以回 `{"type": "ack", "id": "..."}` 表示收到，不回也不影响。
双向通道的 `external_reply` 同时当作 ack。多个前端都连着时以最先回来的那条为准。

### 4.3 三档改法，从轻到重

| 改什么 | 什么时候用 |
| --- | --- |
| **消息 type** | 前端已有协议，靠 `type` 分辨消息，名字对不上 |
| **固定附加字段** | 每条报文都要多带几个固定值，如 `{"source": "仓库A"}`。填一个 JSON 对象，会合并到报文最外层 |
| **整条报文自己写** | 前端连外层 `type / id / data` 都不认。勾上后标准形状全部不要，报文完全由模板决定 |

### 4.4 模板怎么写

```json
{
  "cmd": "newParcel",
  "seq": "{{__id}}",
  "expressNo": "{{expressNo}}",
  "img": "{{imageBase64}}",
  "from": "{{__label}}"
}
```

模板里能用两类占位符：

| 占位符 | 取到什么 |
| --- | --- |
| `{{字段名}}` | **字段映射之后**的字段，如 `{{expressNo}}`。透传模式下就是设备发来的原字段名 |
| `{{__id}}` | 本条消息编号。**必须出现**，否则前端的回复对不上号，保存时会被拦下 |
| `{{__channel}}` / `{{__label}}` / `{{__path}}` | 通道 Key、备注、设备 POST 的路径 |
| `{{__data}}` | 映射之后的整个 `data` 对象 |

**类型规则**：一个值**整串就是一个占位符**时按原类型替换，`"weight": "{{weight}}"` 出来是数字 `12.5`；
占位符夹在文字里（`"第 {{__id}} 号"`）按字符串拼接。写了不存在的占位符会原样留在报文里，方便看出哪里拼错。

页面下方实时预览前端将收到的整条报文。模板不是合法 JSON、缺 `{{__id}}`、引用了映射结果里没有的字段，都会标红并且存不进去。

### 4.5 前端回复样例

同一页最下面「前端回复样例」只在双向通道有意义：自测时内置假前端照它回，
「回给设备 ⚙」页的预览也用它。填一条前端真实会回的 `data` 内容，比如 `{"route": "A"}`。

## 五、配对：两个接口合成一条

设备把一件事拆成两个接口发（图片走 `/upload`，数值走 `/callback`），靠同一个业务号关联。
前端要的是一条带图的完整记录。在两条通道各自的「配对」页设置。

### 5.1 角色

| 角色 | 行为 |
| --- | --- |
| **不参与配对**（默认） | 照常各发各的 |
| **主报文** | 先等同组附加数据齐了，再把合并后的结果发给前端。通常是数值那条 |
| **附加数据** | 收下存进暂存区、**立刻回 200，不推给前端**，等主报文来取。通常是图片那条。数据流被锁成单向 |

一个配对组里**只能有一条主报文**，附加数据可以有多条。谁先到都行。

### 5.2 两边都要填

| 项 | 规则 |
| --- | --- |
| **配对组** | 同组之间才互相配对。只有一组时随便填，两边一样即可 |
| **配对字段** | 用来关联两条数据的字段，**填字段映射之后的名字**。两条通道原始字段名不同时（一边 `code`、一边 `no`），先各自映射成同一个名字 |

### 5.3 主报文那条

| 项 | 默认 | 说明 |
| --- | --- | --- |
| **最多等附加数据** | 5 秒 | 和等前端回复共用同一份超时预算，见第二节 |
| **等不到时** | 照发 | 缺的字段就没有，前端照样收到主数据。或选「回错误」：回 504 配对超时，不发前端 |

### 5.4 附加数据那条

| 项 | 默认 | 说明 |
| --- | --- | --- |
| **并入哪个字段** | 留空 | 留空 = 除配对字段外全部并进主报文；填一个字段名 = 只并这一个 |
| **并进去叫什么** | 留空 | 留空保持原名。填了就改名，比如把 `file` 并进去叫 `imageBase64` |
| **暂存多久** | 60 秒 | 到点没人来取就清掉，最长 3600 秒。暂存条数上限默认 200，满了先丢最早的 |

并入发生在字段映射之后、组装报文之前，所以出向模板里写 `{{imageBase64}}` 也能取到从另一条通道并过来的值。

### 5.5 点「启动服务器」时会检查

只有主报文没附加、只有附加没主报文、一组里多条主报文、两边配对字段不一致，都会拦下并说清怎么改。
自测页的静态体检还会用两条通道的样例试配一次，样例里业务号对不上会提醒。

### 5.6 一个绕不过去的坑

设备如果**在同一个连接上顺序发**：先发主数据、阻塞等响应、拿到响应才发图片，那图片永远发不出去，配对必然超时。
这种设备只能让它**先发图片**，或者两个请求各用各的连接。

## 六、回给设备 ⚙：设备收到的应答

### 6.1 默认形状

```json
{ "success": true, "code": 200, "message": "前端已处理并回复", "forwarded": 1, "data": { "route": "A02" } }
```

出错时 `message` 换成 `error`，`success` 为 `false`。`data` 只在双向拿到前端回复时有。

### 6.2 HTTP 状态码策略

| 选项 | 行为 |
| --- | --- |
| **跟随业务 code**（默认） | HTTP 状态行的码 = 业务 code。超时就是 HTTP 504 |
| **固定 200** | 永远回 HTTP 200，业务码只放在 body 里。有些设备把非 200 一律当网络故障、不看 body，选这个 |

### 6.3 原样回前端回复

勾「双向拿到前端回复时，把前端回的内容原样回给设备（不套外壳）」后，设备收到的 body **就是前端 `external_reply` 里 `data` 的那份内容本身**，没有 `success / code / message` 这层包装。

只影响「拿到前端回复」这一档。单向、没前端连着、超时、JSON 解析失败这些场景没有前端数据可回，仍按下面的外壳或默认形状回。
前端自己在 `data` 里包的那层，程序原样照发，去不掉。

### 6.4 自定义应答外壳

设备接口文档写死了返回字段名（要 `msg` 不要 `message`、不许有多余字段）时，勾「自定义应答外壳」写模板。「常用形状」下拉里有三个现成的可以直接套：

```json
{ "success": "{{__success}}", "code": "{{__code}}", "msg": "{{__message}}", "data": "{{__data}}" }
```

| 变量 | 取到什么 |
| --- | --- |
| `{{__success}}` | 布尔值，业务 code < 400 |
| `{{__code}}` | 数字，业务状态码 |
| `{{__message}}` | 提示文案，来自应答表（6.5） |
| `{{__data}}` | 双向拿到的前端回复；没有时为 `null` |
| `{{__forwarded}}` | 这条数据推送给了几个前端 |
| `{{__scene}}` | 命中的场景 key，如 `ok_reply`、`reply_timeout` |
| `{{__channel}}` | 通道 Key |

类型规则和出向模板一样：整串是一个占位符按原类型出，`"code": "{{__code}}"` 出的是数字 `200`。
模板里没写的字段就不会出现，比如不写 `forwarded` 设备就看不到它。
模板必须用到 `{{__code}}` 和 `{{__message}}`，否则存不进去。预览用的是「双向拿到前端回复」那一档。

### 6.5 状态码和文案：按场景改

「获取数据配置」旁边的「**HTTP 响应**」按钮，一张全局表，改完点确定立即生效，不用重启：

| 场景 | 默认码 | 什么时候返回 | 可用占位符 |
| --- | --- | --- | --- |
| 接收成功（单向） | 200 | 单向转发给前端后立即返回 | |
| 接收成功（双向） | 200 | 双向拿到前端回复后返回 | |
| 请求体不是合法 JSON | 400 | body 解析失败 | `{error}` |
| 请求体过大 | 413 | body 超过 16MB | `{limit}` |
| 没有前端连接 | 503 | 双向下一个前端都没连着 | |
| 排队超时 | 503 | 单发模式排到超时都没轮到 | `{timeout}` |
| 等待回复超时 | 504 | 双向下前端没在超时内回复 | `{timeout}` |
| 路径没有对应通道 | 404 | 路径没匹配上，也没有兜底通道 | `{path}` |
| 字段转译失败 | 400 | 必填字段缺失或转换出错，数据没转发 | `{error}` |
| 配对超时 | 504 | 主报文没等到附加数据，且设了「回错误」 | `{missing}` `{timeout}` |
| 文件过大 | 413 | 字段映射里配了文件校验，解码后超过上限 | `{limit}` |
| 文件解析失败 | 415 | 配了文件校验的字段为空、不是 base64、格式不对 | `{error}` |

叠加顺序：**通道自己的覆盖 > 这张全局表 > 出厂默认**。按通道覆盖目前只能手改配置文件里的 `responses`，见第七节。
码只接受 100–599，认不出的场景会被忽略。

## 七、配置文件里长什么样

「导出」出来的 `.json`，一条通道的完整结构（只列高级配置相关的部分）：

```jsonc
{
  "key": "sorter_data",
  "label": "分拣数值",
  "path": "/callback",
  "flow": "twoway",                 // oneway / twoway
  "timeout": 15.0,
  "dispatch": "concurrent",         // concurrent / serial
  "mapping": {
    "mode": "pick",                 // passthrough / pick / merge
    "on_missing": "error",          // error / skip / default
    "fields": [
      { "source": "code",   "target": "expressNo", "transforms": [],         "required": true,  "default": "" },
      { "source": "weight", "target": "weight",    "transforms": ["number"], "required": false, "default": "" },
      { "source": "no",     "target": "orderNo",   "transforms": ["trim", {"op": "prefix", "value": "SF"}] },
```

改完「导入」回去即可。写错的值不会让程序崩，会落回默认。

## 八、现成的例子：几何智造分拣设备

内置模板「几何智造分拣设备」（带图）和「几何智造分拣设备（无图片）」就是照设备文档
[对接几何智造分拣设备文档](对接几何智造分拣设备文档.md) 配出来的，可以当参考答案看：

| 文档要求 | 对应配置 |
| --- | --- |
| 所有接口返回 `success / code / msg / data` | 两条通道都套了自定义应答外壳 |
| 成功 `msg` 为「操作成功」 | 通道 `responses` 覆盖 `ok` / `ok_reply` 的文案 |
| 文档里的 404「服务器接口错误」/ 500「服务器逻辑错误」 | 那是前端页面那一侧回的。Print Bridge 自己答复的出错场景**不覆盖**，用默认文案带具体原因：400「字段转译失败：缺少必填字段 code」、504「等待前端回复超时（15s）」等，排错时一眼能看出是哪里的问题 |
| `/upload` 图片 ≤2M，仅 jpg/png/pdf，413 / 415 | `file` 字段带 `check`，`file_too_large` → 413「文件超过 2M 限制：…」，`file_invalid` → 415「文件解析失败：…」，冒号后面是具体原因 |
| `/callback` 成功时回分拣结果（`route` 等） | 由前端页面回复，所以这条通道是**双向**，超时 15 秒。并且勾了「原样回前端回复」：前端回的整份内容直接交给设备，不再套 `success/code/msg` |
| `/upload` 的 `data` 固定 `null` | 单向通道没有前端回复，`{{__data}}` 自然是 `null` |

## 九、改完怎么验证

1. **看预览**。字段映射、发给前端、回给设备三页各有实时预览，预览就是运行时的结果。
2. **跑自测**。启动服务后到「自测」页签点「开始自测」。静态体检会查配对字段是不是映射后的名字、外壳缺不缺字段；用例会按样例真发请求，比对状态码和 body 形状。
3. **看日志**。三行对应三个环节：

| 日志 | 看什么 |
| --- | --- |
| `📥 [通道] 接收数据` | 设备发来的原始数据 |
| `📤 已推送给 N 个 WebSocket 客户端` | 转给前端了 |
| `📨 回给设备 HTTP 200（ok_reply）: {...}` | **设备实际收到的状态码和 body**，改了外壳对这一行就知道生效没有 |

4. **用命令模拟设备**。「基础」页「这条通道怎么用」里的 `curl` 命令复制出来跑一下，终端里看到的就是设备会收到的。

## 附录：占位符速查

| 用在哪 | 占位符 |
| --- | --- |
| 发给前端的模板 | `{{映射后的字段名}}` `{{__id}}`（必须） `{{__channel}}` `{{__label}}` `{{__path}}` `{{__data}}` |
| 回给设备的外壳 | `{{__success}}` `{{__code}}`（必须） `{{__message}}`（必须） `{{__data}}` `{{__forwarded}}` `{{__scene}}` `{{__channel}}` |
| 应答表的文案 | `{error}` `{timeout}` `{limit}` `{path}` `{missing}`（单花括号，按场景可用） |

模板占位符是**双花括号**，应答文案占位符是**单花括号**，两套别混。
