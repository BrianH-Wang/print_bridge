# 对接：几何智造分拣设备

设备侧接口文档见对方提供的《对接几何智造分拣设备文档》。本文只记录
**print_bridge 这边要做什么**，以及怎么在浏览器还没开发好的情况下先跑通。

## 1. 设备要的两条链路

| 接口 | 方向 | 设备期望的应答 | 谁提供应答内容 |
|---|---|---|---|
| `POST /callback` 条码+重量+体积 | **双向** | `data` 里要带 `route` 分拣格口 | 前端浏览器算出来的 |
| `POST /upload` 条码+图片 base64 | **单向** | `data` 固定 `null`，立刻返回 | 本程序自己回 |

两条靠 **`code`（条码值）配对**，合并成一条推给浏览器。

设备文档里写「图片请通过上传接口以相同的 code 单独上传」，但**没规定先后**，
两种顺序都要接得住。

## 2. 实测差距（已全部修掉）

下表是**当初**对着第一版跑出来的结果。1/2/4 在一期修掉（通道路由 + 应答外壳），
3/5 在二期修掉（字段转译 + 配对合流），6/7/8 靠通道的应答覆盖和字段校验配置解决。
现在 `tools/mock_device.py` 跑下来是全绿的，两种到达顺序都能合并成一条给前端。

用 `tools/` 下两个脚本对着现版本跑出来的结果（`tools/mock_device.py` 会自动校验）：

| # | 问题 | 现状 | 设备要求 |
|---|---|---|---|
| 1 | 应答字段名 | `message` / 失败时 `error` | 一律 `msg` |
| 2 | 多余字段 | 额外塞了 `forwarded` | 文档只有 success/code/msg/data |
| 3 | 路径不区分 | `/upload` 和 `/callback` 走同一套逻辑 | 两条语义完全不同 |
| 4 | `/upload` 被当成双向 | 阻塞等前端，还把 `route` 回给了上传接口 | 立刻回，`data: null` |
| 5 | 没有配对 | 前端收到两条独立报文，数值那条不带图 | 合并成一条 |
| 6 | 错误码对不上 | 用 400/503/504 | 只认 404/500/413/415 |
| 7 | 缺 415 场景 | 没有「文件解析失败」 | base64 解不开或非 jpg/png/pdf |
| 8 | 体积上限口径不同 | 按整个 body 的 Content-Length，16MB | 按 **base64 解码后**，2MB |

第 1、2 条对所有对接方都会遇到——**说明应答外壳必须可配置**，不能只让改状态码和文案。

## 3. 实际配置

两条通道，照下面配就能对接。界面上填在通道对话框的对应页里。

```jsonc
[
  {
    "key": "sorter_data", "label": "分拣数值", "path": "/callback",
    "flow": "twoway", "timeout": 15,

    // 「字段映射」页：设备的 code 前端要叫 expressNo
    "mapping": { "mode": "pick", "on_missing": "error", "fields": [
      { "source": "code",   "target": "expressNo", "required": true },
      { "source": "weight", "target": "weightKg", "transforms": ["number"] },
      { "source": "length", "target": "lengthCm", "transforms": ["number"] },
      { "source": "width",  "target": "widthCm",  "transforms": ["number"] },
      { "source": "height", "target": "heightCm", "transforms": ["number"] }
    ]},

    // 「配对」页：主报文，等图齐了再发
    "pair": { "role": "primary", "group": "parcel", "field": "expressNo",
              "wait": 5, "on_missing": "send_partial" },

    // 「回给设备 ⚙」页：设备要 msg，且不认多余字段
    "envelope": { "success": "{{__success}}", "code": "{{__code}}",
                  "msg": "{{__message}}", "data": "{{__data}}" },
    "responses": { "bad_json":      { "code": 404 },
                   "reply_timeout": { "code": 500, "message": "服务器逻辑错误" },
                   "no_client":     { "code": 500, "message": "服务器逻辑错误" } }
  },
  {
    "key": "sorter_image", "label": "分拣图片", "path": "/upload",
    "flow": "oneway",

    "mapping": { "mode": "pick", "fields": [
      { "source": "code", "target": "expressNo", "required": true },
      { "source": "file", "target": "imageBase64" }
    ]},

    // 附加数据：收下就回 data:null，不推前端，等主报文来取
    "pair": { "role": "attach", "group": "parcel", "field": "expressNo",
              "keep": 60, "max_pending": 200 },

    "envelope": { "success": "{{__success}}", "code": "{{__code}}",
                  "msg": "{{__message}}", "data": "{{__data}}" },
    "responses": { "ok": { "message": "操作成功" } }
  }
]
```

**配对字段填 `expressNo` 而不是 `code`**：配对键取的是**转译之后**的名字。
两条通道都先把 `code` 改成 `expressNo`，配对时就对得上。

前端收到的是合并后的一条：

```jsonc
{ "type": "external_data", "id": "…", "channel": "sorter_data",
  "expectReply": true,
  "data": { "expressNo": "CCSL2026083100123", "weightKg": 12.5,
            "lengthCm": 40.75, "imageBase64": "iVBORw0KGgo…" } }
```

### 配对的关键点

**先到的那条不需要挂起。** `/upload` 是单向的，收下图存进暂存区、立刻回 200 就完事。
只有 `/callback` 需要等——先等图（`wait`），再等前端回 `route`。

**这两段等待共用一份超时预算**，和单发模式一个做法，否则设备实际要等
`wait + timeout`，比配置的数字长一倍。

**暂存区有上限和过期时间**。只传图不推数据的话，2MB 一张挂着不清会把内存吃光；
`keep` 到点自动清，`max_pending` 满了丢最早过期的那些。

### ⚠️ 设备发送顺序的限制

设备如果**用同一个连接顺序发**——先发 `/callback`、阻塞等响应、拿到响应才发 `/upload`——
那图片永远发不出去，配对必然超时。这种设备只能让它**先发图片**，
或者把两条请求放在各自独立的连接上。

`tools/mock_device.py --parallel` 模拟的就是后者；不加 `--parallel` 时是顺序发，
正好可以用来复现这个坑。

## 4. 还没做的两条

第 7、8 条（`415` 文件解析失败、按 base64 **解码后** 2MB 判 `413`）需要「内容校验」，
也就是 [高级配置.md](高级配置.md) 里的 X2，还没实现。现在的行为是：

- 体积按整个 body 的 `Content-Length` 判，上限 16MB —— 比设备文档宽松，不会误拒。
- base64 解不开或格式不对时**不会**报 415，图片会原样透传给前端。

真要严格对齐设备文档的话再补 X2；不补也能跑通，只是宽进。
识别文件类型的现成能力已经有了（`history_store.sniff()` 认得 jpg/png/pdf）。

## 5. 浏览器没开发好之前怎么跑

```bash
# 1. 起 print_bridge（WS 8765 / HTTP 13213，数据流选双向）

# 2. 另开一个终端，用假前端顶上
python tools/mock_frontend.py --port 8765

# 3. 再开一个，模拟设备发两条请求
python tools/mock_device.py
```

`mock_device.py` 会逐条校验返回结构，把不符合文档的地方列出来。

常用变体：

```bash
# 配对：两种到达顺序都该合并成一条
python tools/mock_device.py                                  # 图片先到
python tools/mock_device.py --order data-first --parallel    # 数值先到（必须 --parallel，见上）
python tools/mock_device.py --no-image                       # 只推数值，测配不上时的表现

python tools/mock_device.py --image ./label.jpg  # 用真实图片
python tools/mock_frontend.py --no-reply         # 前端不回，测设备侧超时
python tools/mock_frontend.py --delay 3 --pdf    # 前端慢 3 秒，回复带标签 PDF
```

配对生效时，`mock_frontend` 应该**只打印一条** `external_data`，
并且那一条带 `🖼 带图片字段 imageBase64`——两条都打印出来就说明没合并上。

给前端开发的人：`mock_device.py` 可以当成设备的替身，不用等真机就能联调。
